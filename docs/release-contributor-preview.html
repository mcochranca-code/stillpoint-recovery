01 / Release path

One deliberate tag.

The release workflow is intentionally narrow: it validates the version, proves the app still builds, then publishes the allowlisted package with npm provenance.

01 — PREPARE

Update version

Change package.json to the next unused semantic version.

02 — TAG

Push vX.Y.Z

The workflow runs only for tags matching v*.*.*.

03 — VERIFY

Match exactly

The tag must equal v${package.version} or publishing stops.

04 — PROVE

Run gates

Typecheck, lint, 51 tests, and the production PWA build must pass.

05 — PUBLISH

Provenance

npm publishes the allowlisted package publicly using NPM_TOKEN.

!
Package boundary matters.

The npm allowlist includes app source, runtime assets, build files, README, and MIT license metadata. The NA PDF, copyright directory, repository workflows, and README-only media are excluded.

02 / Contributor practice

Make the quiet parts count.

Contributors protect user control, privacy, accessibility, and the difference between supportive software and clinical claims.

Privacy

Local by default

  • No hidden uploads, analytics, account requirements, or remote persistence.
  • Keep IndexedDB and backup behavior explicit and reversible.
  • Never claim encryption or guaranteed offline persistence without evidence.
Interface

Gentle and operable

  • Preserve keyboard access, visible focus, text scaling, and high contrast.
  • Respect reduced motion and discreet-mode behavior.
  • Confirm destructive actions and explain what will be deleted.
Content

Clear rights boundaries

  • Prefer official publisher links for recovery resources.
  • Keep third-party literature link-only unless authorization is documented.
  • Maintain attribution and non-affiliation notices.

05 / Pull request checklist

Leave a clear trail.

Every change should tell the next contributor what moved, why it matters, and how it was checked.

Before openingWhat to include
Branch and scopeUse a focused branch and keep one behavior or documentation concern per pull request when possible.
BehaviorDescribe user-facing changes, privacy impact, migration concerns, and accessibility decisions.
EvidenceList typecheck, lint, tests, coverage, build, and documentation checks that were run.
Visual changesInclude screenshots or a short recording for responsive, reduced-motion, or interaction changes.
BoundariesCall out changes to external links, copyright, service-worker caching, IndexedDB, backup formats, or release metadata.
